# Steamrentlibrarysoft\n\n![tests](https://github.com/onix312/Steamrentlibrarysoft/actions/workflows/tests.yml/badge.svg)

Локальное **desktop**-приложение (не веб) для управления продажей доступа
к играм через **Steam Families** на площадке **FunPay**.

```
Steam-аккаунты → библиотеки → семейная библиотека → доступные игры
→ анализ спроса → объявления FunPay → заказы → клиенты → сроки доступа
→ освобождение семейных слотов → статистика
```

Одно окно — весь рабочий процесс: несколько собственных Steam-аккаунтов,
объединённых в Steam Families, сдача доступа к играм в аренду, учёт заказов,
таймеры доступов и аналитика.

## Возможности (MVP)

* **Steam**: любое число аккаунтов, синхронизация библиотек через официальный
  Steam Web API (`IPlayerService/GetOwnedGames`, ключ из системного хранилища)
  или офлайн-режим симуляции; метаданные игр (цены, жанры, отзывы).
* **Единая семейная библиотека**: одинаковые AppID объединяются в одну запись
  со списком аккаунтов-владельцев и количеством копий; мгновенные фильтры
  (все / можно продавать / нельзя / требует проверки / бесплатные / платные /
  популярные / есть свободный слот / все заняты / дубликаты / по аккаунту).
* **Проверка Steam Families** (`FamilyEligibilityService`, вне GUI):
  статусы «Доступна / Недоступна / Требует проверки / Сторонний launcher /
  Исключена издателем / Бесплатная / Нет смысла продавать», кэш с датой и
  источником проверки, ручные переопределения. Официального публичного API
  eligibility нет — см. `docs/RESEARCH.md`.
* **Demand Score 0–100 и Commercial Score**: прозрачные факторы
  (популярность, отзывы, цена, актуальность, мультиплеер/кооп, тренд,
  история продаж), веса — в настройках; грейды **S/A/B/C/D/FREE**.
  F2P (CS2, Dota 2, Apex и т.п.) не считается коммерческим преимуществом.
* **Заказы и клиенты**: ручной ввод и импорт, статусная модель
  (Новый → Настройка Steam → Активен → Скоро закончится → Завершён…),
  чёрный список, заметки, минимум персональных данных.
* **Доступы (`AccessLease`) + `LicenseAllocator`**: система знает,
  *какая лицензия → какому клиенту → до какой даты отдана*; одна копия не
  может быть продана дважды одновременно; выбор наименее нагруженной копии;
  автоосвобождение лицензии по истечении срока; продление; таймеры в таблице.
* **Пакеты (`GameBundle`)**: ручные и автопредложения по жанрам и спросу.
* **Объявления**: генерация редактируемых текстов
  («Название | Steam Family | Доступ N дн.», описание, FAQ, условия,
  сообщение после покупки); публикация на FunPay — вручную в безопасном
  режиме либо автосинхронизацией лотов в неофициальном режиме (см. ниже).
* **`FunPayAdapter`** с декларируемыми возможностями
  (`AVAILABLE`/`MANUAL`/`UNSUPPORTED`): официальный публичный API у FunPay
  отсутствует, поэтому по умолчанию используется ручной режим;
  неофициальный режим `golden_key` выключен и помечен как рискованный.
* **Планировщик** (фоновые задачи, экспоненциальный backoff), **уведомления**
  (центр в приложении + системный трей), **журнал операций** (audit),
  **аналитика** (выручка, загрузка лицензий, рекомендации отдельно от фактов),
  резервные копии БД.
* **Режимы безопасности**: `DRY RUN` по умолчанию, `Manual approval` для
  сообщений, никакого обхода CAPTCHA/2FA/Steam Guard/антибот-защит.

## Быстрый старт

На Windows достаточно запустить:

```bat
start.bat
```

Скрипт создаёт `.venv`, устанавливает зависимости только при изменении
`requirements.txt`, выполняет import-smoke и запускает приложение.

Ручной запуск:

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python run.py
```

При первом запуске в режиме симуляции приложение предложит добавить
4 демо-аккаунта и сразу построит библиотеку, статусы семейного доступа и
оценки спроса. Для реальной работы: Настройки → режим **Live**, добавьте
ключ с <https://steamcommunity.com/dev/apikey> (ключ сохраняется в
Windows Credential Manager через `keyring`, в БД — только ссылка).

### Тесты

```bash
python -m pytest tests/ -q
```

Критическая логика покрыта тестами: `LicenseAllocator` (занятая копия не
выдаётся повторно, выбор свободной копии при нескольких владельцах),
истечение аренды → освобождение лицензии, дубликаты AppID → одна игра и
несколько лицензий, F2P вне коммерческого каталога, недоступные игры не
продаются, DRY RUN блокирует внешние изменения.

### Сборка .exe

```bash
pip install pyinstaller
pyinstaller --windowed --name SteamRentManager ^
    --add-data "app/integrations/steam/data;app/integrations/steam/data" run.py
```

## Архитектура

```
app/
  main.py, app_context.py   # сборка слоёв, точка входа
  core/                     # конфиг, события, логирование, планировщик, секреты, часы
  domain/                   # enums, value objects — без Qt и БД
  database/                 # SQLAlchemy 2.x: модели, TZ-aware SQLite, репозитории
  services/                 # бизнес-логика: библиотека, eligibility, спрос,
                            # аренды/аллокатор, заказы, объявления, пакеты,
                            # аналитика, уведомления, аудит, FunPay-фасад
  integrations/
    steam/                  # официальный Web API, симулятор, метаданные,
                            # правила семей (кулдауны/слоты), датасет исключений
    funpay/                 # адаптер + возможности + шаблоны текстов
  workers/                  # QRunnable-воркеры: синхронизация, опрос
  ui/                       # PySide6: тёмная тема, 13 экранов, диалоги
tests/                      # pytest: критические сценарии ТЗ
docs/                       # RESEARCH.md (ограничения сервисов), ARCHITECTURE.md
```

Правило зависимостей: `UI → services → (database, integrations) → domain`.
GUI никогда не блокируется: сетевые операции выполняются воркерами в пуле
потоков, обновления интерфейса — только из главного потока.

Полное описание схемы БД и инвариантов — в `docs/ARCHITECTURE.md`,
результаты исследования ограничений сервисов — в `docs/RESEARCH.md`.

## Безопасность

* Пароли не запрашиваются и не хранятся; секреты — только в системном
  хранилище (`keyring`), в БД/конфиге — ссылки `keyring://...`.
* Приложение не управляет составом семьи программно и не обходит ограничения
  Steam (кулдауны, слоты, региональные требования — только учитываются).
* Никакого обхода CAPTCHA/2FA/Cloudflare/антибот-защиты и лимитов.
* Рискованные действия требуют подтверждения; сообщения клиентам по умолчанию
  отправляются только после ручного одобрения.

## FunPay Automation OS (новый контур)

Отдельный слой поверх базового MVP — локальная операционная система продавца
(домены: `app/services/os`, `app/services/drops`, `app/engines`, UI-страницы
«Продукты», «Склад», «Воркфлоу», «Рынок», «Drops Центр», «Drops Сессии»).

* **Каталог продуктов и фабрика**: продукты типа `auto / semi_auto / manual`
  с уровнем автоматизации `A0–A5`, себестоимостью, ценой и минимальной ценой.
  Фабрика разворачивает движок игры (например, Project Zomboid) в набор разных
  реальных продуктов: конфиги, мод-паки, сервер под ключ, ремонт сохранений.
* **Цифровой склад** (`StockService`): юниты со статусами
  `готовится/готов/выставлен/резерв/продан/истёк/проблема`. Резервирование —
  атомарный условный UPDATE в транзакции: при гонке двух заказов товар
  достаётся ровно одному. Дефицит (`готово < цель`) порождает задачи пополнения.
* **Движок воркфлоу** (`WorkflowEngine`): встроенные сценарии
  «авто-выдача», «полуавто-диагностика», «сервер под ключ», «ручная услуга».
  Шаги: авто / ручной / подтверждение / валидация / выдача. Внешние действия
  в режиме помощника всегда требуют подтверждения; в `DRY RUN` выдача
  ограничивается превью и ничего не уходит наружу.
* **Диагностика и фабрики конфигов** (`app/engines`): Server Doctor
  (классификация проблемы по логам/описанию + фикс + откат), Mod Doctor
  (зависимости, версии, дубликаты, порядок загрузки), Config Factory
  (пресеты конфигов с README, инструкцией и планом отката). Изменения к
  системе и сейвам никогда не применяются автоматически.
* **Рыночный радар**: снапшоты цен конкурентов (ввод ручной — сбор не
  обходит защиты маркетплейса), ценовые стратегии
  `агрессивная/сбалансированная/рыночная/премиум` с учётом минимальной цены,
  Opportunity Score 0–100 → `CREATE PRODUCT / WATCH / SKIP`.
* **Drops Control Center**: кампании, аккаунты, сессии просмотра, приоритеты
  по ценности/час и дедлайну, оценка «продать сейчас / добить кампанию».
  Прогресс дропов подтверждается только вручную по инвентарю — фальшивый
  просмотр и обход защит исключены архитектурой (см. `docs/RESEARCH.md` §5).
* **Режимы безопасности**: `АВТОМАТИЗАЦИЯ ВЫКЛЮЧЕНА / РЕЖИМ ПОМОЩНИКА /
  АВТО БЕЗ ОПАСНЫХ ДЕЙСТВИЙ` + глобальный `DRY RUN`. Все секреты — в
  системном хранилище (`keyring`); в БД только ссылки `keyring://...`.
* **Импорт заказов** (`FunPayImportService`): заказ сопоставляется с продуктом
  по коду/названию в лоте и уходит в воркфлоу; несопоставленные заказы
  сохраняются для ручной привязки (экран «FunPay»).
* **Неофициальный режим FunPay** (выключен по умолчанию): собственный клиент
  `golden_key` (написан с нуля, чужой код не копировался) читает свои заказы
  со страницы «Мои продажи», чаты и отправляет сообщение с товаром в чат
  заказа (автовыдача). Лимиты частоты уважаются, секреты — только в системном
  хранилище; риски ограничений аккаунта — на операторе.
* **Живой цикл заказов**: поллинг синхронизирует статусы — «закрыт» на
  FunPay завершает наш заказ (юнит помечается проданным), «возврат» отменяет
  заказ и освобождает резерв склада. О новых заказах, возвратах и
  непривязанных лотах приходят уведомления (центр уведомлений + трей),
  просроченные назначения в очереди подсвечивает движок правил. На экране
  «Заказы» видны продукт ОС и статус воркфлоу; несопоставленный заказ можно
  привязать к продукту (с запуском воркфлоу) и подтвердить выдачу вручную.
* **Входящие сообщения чатов**: неофициальный режим читает непрочитанные
  чаты (до 10 за опрос, до 5 последних входящих из чата), сохраняет
  сообщения с дедупликацией по внешнему ID. Автоответы настраиваются парами
  «команда = ответ» (префикс, без учёта регистра): в `АВТО БЕЗ ОПАСНЫХ
  ДЕЙСТВИЙ` без `DRY RUN` ответ уходит сам, в остальных режимах —
  сохраняется черновиком на подтверждение оператору.
* **Автосоздание и закрытие лотов** (неофициальный режим): продукты ОС
  синхронизируются с лотами FunPay — активный продукт с товаром на складе
  получает лот в настроенной подкатегории («Имя игры = ID» в настройках),
  при выключении продукта или обнулении склада лот закрывается (деактивация
  без удаления, обратимо), при восстановлении — открывается заново. Только
  после подтверждения оператора (или автосинхронизация в `АВТО БЕЗ ОПАСНЫХ
  ДЕЙСТВИЙ` без `DRY RUN`, выключена по умолчанию); каждое действие — в
  аудит-журнал. Экран «FunPay»: план синхронизации, таблица лотов, кнопка.
* **Синхронизация цен лотов**: цена продукта транслируется в цену лота —
  с настраиваемым допуском расхождения (%), без изменения остальных полей
  лота и с защитой: цена ниже минимальной продукта не публикуется (лот
  не трогаем, оператору выводится предупреждение). Работает теми же
  предохранителями, что создание/закрытие лотов.
* **Операторы и очередь** (`QueueService`, экран «Очередь»): назначения на
  ручные услуги с автоподбором исполнителя (по игре и загрузке) и корзинами
  `сейчас / сегодня / завтра / ожидание`.
* **Аналитика ОС** (экран «Доходы»): выручка и прибыль по типам
  `AUTO / SEMI_AUTO / MANUAL`, ручное время, прибыль/час, рекомендации
  `KILL / OPTIMIZE / SCALE / KEEP`.
* **Движок правил** (`app/engines/rules_engine.py`): декларативные правила
  «дефицит склада → задача пополнения», «кампания заканчивается → напомнить»,
  «воркфлоу долго ждёт подтверждения → уведомить» и т. п.; только подсказки
  и задачи, никаких деструктивных действий.


## Production Platform v2

* **Production DB**: схема версионируется Alembic; существующая pre-Alembic
  база перед первым stamp проходит `PRAGMA integrity_check` и резервируется.
  Перед реальным upgrade также создаётся SQLite backup; доступно проверенное
  восстановление из backup. Текущие revision/schema version доступны через
  `Database.schema_revision` / `Database.schema_version`.
* **CI**: Windows, Python 3.11/3.12, полный pytest, import smoke, AppContext
  smoke и Qt offscreen smoke.
* **Operations Center**: стартовый экран собирает проблемы интеграций, новые
  заказы, ручные workflow checkpoints, входящие сообщения, stock deficit,
  истекающие аренды и Drops actions в одну приоритетную очередь.
* **Fulfillment Engine Registry**: workflow выбирает движок из product metadata,
  а не вызывает Server Doctor напрямую. Встроены Server/Mod/Game/Save Doctor,
  Config Factory и Digital Delivery.
* **Product Packs**: каталог вынесен в versioned JSON. Обновление pack меняет
  технические параметры, но сохраняет заданные оператором цену и minimum price.
  Базовый pack покрывает Project Zomboid, Minecraft, 7 Days to Die, Terraria,
  Valheim, Enshrouded, Palworld, Space Engineers, RimWorld, ARK, Ready or Not,
  Phasmophobia, R.E.P.O., The Forest, Raft, Don't Starve Together и Rust.
* **Market Radar v2**: временные ряды, изменения median/competition, связь с
  нашими продажами, решения CREATE/SCALE/HOLD/KILL и предложения цены лотов.
* **FunPay Protocol Health**: contract fixtures для auth/orders/chat/runner/lots
  и circuit breaker. При подозрении на изменение протокола автоматические
  FunPay-capabilities выключаются до успешной проверки.
* **Drops v2**: единый Campaign → Account → StockUnit inventory, valuation,
  production queue, browser profile linkage и синхронизация reserve/release/sold
  с универсальным цифровым складом.

## Ограничения (честно)

* Официального публичного API у **FunPay** нет: публикация объявлений и
  переписка выполняются оператором; приложение готовит тексты и ведёт учёт.
* Официального признака «игра доступна в Steam Families» нет: статус строится
  на датасете исключений, метаданных и ручных проверках (кэшируется).
* Режим симуляции — для офлайн-работы, демо и тестов; данные в реальном
  режиме приходят только из официального Steam Web API.
